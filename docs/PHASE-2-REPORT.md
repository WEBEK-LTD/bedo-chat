## Independent review

A separate reviewing agent audited the Phase 2 code against the specification and reproduced each finding
against the real stack. Its first pass found four high-severity problems, all fixed and covered by
regression tests (`apps/api/test/security.integration.test.ts`):

1. Parallel requests could exceed the 5 wrong 2-Step passwords per sign-in and the hourly in-session limit.
   Attempts are now counted before the password is checked.
2. The same race applied to admin authenticator codes. Fixed the same way; a pending admin sign-in can be
   used only once.
3. Refresh-token reuse detection only remembered the last rotated token, so a thief who rotated twice was
   not detected. Every rotated token is now remembered per session (an hourly worker job removes them once
   they cannot matter).
4. Expiry timing let an attacker tell listed from unlisted numbers. Every code request now creates the same
   kind of challenge.

Medium and low findings fixed: admin routes no longer accept the web app's origin (and the reverse, new
`ADMIN_ORIGINS`); push subscriptions accept only browser push services, and one user cannot take over
another's live subscription; the per-IP limit counts IPv6 per /64 and is shared by all code types; a
phone-change code works only for the account that asked for it; a number taken mid-change gives a clean
conflict; refused Moderator actions are audited; login alerts no longer repeat a client-chosen device name.

The second pass confirmed these and found one regression in fix 4 (a guessed never-sent code would have
succeeded), now fixed twice over: such a challenge can never succeed, and an account is created or a number
changed only after re-checking the academy list. It also flagged that the retired-token table needed
pruning and that one query scanned all sessions; both fixed.

   its cache key. After a plain `pnpm build` in the same folder, `netlify deploy --build` from your machine

   build output"). Builds on Netlify start from a fresh clone and are not affected, which matches your
   successful Phase 1.2 deployment. Workaround: run `TURBO_FORCE=true netlify deploy --build ...`. Proposed
   fix: add `NEXT_PRIVATE_STANDALONE` to the build task's `env` in `turbo.json`. Not changed because
   Phase 1 is frozen (R-02); approval needed.

**How Netlify serves the admin pages (checked in Netlify's own code, `netlify-cli` 27.10.2).**
- Netlify's Next.js runtime (v5.16.1) copies the web app's `public/` folder, including `admin/`, to the CDN.
  Its server function has the path `/*` and `preferStatic: true`.
- For each request, Netlify first looks for a matching static file. Only if there is none does it run the
  Next.js server function. Redirect rules come after both, so on this site they are never reached.
- Netlify's static file matching tries `<path>.html` and `<path>/index.html`. So `/admin` and `/admin/` find
  `admin/index.html`, and `/admin/login` and `/admin/login/` find `admin/login.html`. No routing rule is
  needed.
- My first version added two rewrite rules for this. The independent review showed they could never run, so
  they were removed. The browser-test stand-in now follows Netlify's real order: static file with the site's
  headers first, then the Next.js server.
- Netlify documents that "Rewrites in Next.js configuration can't point to static files in the public
  directory", and headers in `next.config` don't reach those files either. That's why the admin security
  headers are in `netlify.toml`.

**`apps/admin/netlify.toml` (owner constraint C): kept.**
- **What reads it:** Netlify, only for a site whose package directory is `apps/admin` or a CLI command with

- **What doesn't:** local development and the browser tests.
- **Why it stays:** removing it is not necessary for D-26. It now says at the top that it is not the
  production configuration and must never be used to deploy.

- **Low (documented):** running only the web app's own build script, outside Turborepo, would add whatever
  admin export was built last. The guide says to build through Turborepo, as Netlify does.
- **Low (unchanged by choice):**
  - The two builds receive the same environment variables as every other build (the existing Phase 1/2

  - Running the bundle check inside the Netlify build command is a possible later hardening. It would change

**Behaviour notes.**
- Moving from the dashboard's sign-in page to `/admin` inside the app loads the page fully instead of

## Phase 2.3.1

**Decision.** D-27, recorded in the blueprint and in `docs/DECISIONS.md` before implementation.

**Why.** After Phase 2.3 the real `bedochat` site kept building from `apps/admin`. That setting is stored in
Netlify, and the repository cannot override it: Netlify reads the `netlify.toml` of the site's Package directory
first. Netlify's own app detection lists `apps/admin` before `apps/web`. `apps/admin/netlify.toml` was still a
working site configuration, so the wrong setting gave a "successful" deploy: the Admin Dashboard alone at the
site root, with its scripts missing, so the pages stayed on "Loading…". The build also had no
`NEXT_PUBLIC_API_URL`, because it was only expected as a Netlify UI setting.

**Fresh-unpack verification** gains two checks:

## Phase 2.3.2

**Decision.** D-28, recorded in the blueprint and in `docs/DECISIONS.md` before implementation.

**Evidence.** The real Netlify build log showed the existing `bedochat` site still building with Package
directory `apps/admin` (publish `/opt/build/repo/apps/admin/.next`), and the D-27 guard stopping it. The
repository was correct, but production depended on one Netlify UI setting that the repository cannot set.

**Finding** (from Netlify's own code, `@netlify/config` and `@netlify/plugin-nextjs` 5.16.1, then confirmed
with real `netlify build` runs):
- The Package directory decides only two things: which `netlify.toml` Netlify reads, and where Netlify keeps
  its working files.
- The Next.js runtime finds the app, its `public/` folder and its server function from the build output
  (`requiredServerFiles.appDir`, here `apps/web`).
- So if the `netlify.toml` Netlify reads under `apps/admin` describes the one-site build, a site set to
  `apps/admin` publishes exactly the same combined site.

| Change | Where |
| --- | --- |
| Replaced with a byte-for-byte copy of the production site configuration (build `pnpm turbo run build --filter=@bedo/web`, publish `apps/web/.next`, `NEXT_PUBLIC_API_URL`, admin security headers). The D-27 guard is removed; it is superseded | `apps/admin/netlify.toml` |
| Header comment explains the two identical copies | `apps/web/netlify.toml` (settings unchanged) |
| Both config files must build the one site (Phase 1.2 config test) | `scripts/checks.test.mjs` |
| The two files must be byte-identical and build the web app; the guard must be gone; both carry the API URL | `scripts/one-netlify-site.test.mjs` |
| Docs | `docs/DEPLOYMENT.md`, `docs/DECISIONS.md`, this report |

**Checked with Netlify's real build tooling** (`netlify build --offline`), from a fresh unpack:
- **From `apps/web`:** the combined site, as before.
- **From `apps/admin`:** Netlify reads `apps/admin/netlify.toml`, runs the same build, publishes
  `apps/web/.next`, and passes every one-site check:
  - student app and `/sw.js`;
  - `/admin` and `/admin/login` from the admin export, with every `/admin/_next` file present;

  - both apps built with `https://bedochat.com/api`;

- **Both builds deploy the same files**, compared file by file with only the random build ids ignored.

**Unchanged:**
