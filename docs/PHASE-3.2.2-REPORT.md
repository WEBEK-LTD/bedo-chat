# Phase 3.2.2 report — production deployment from the dashboards (D-37)

Phase 3.2.2 changes no application code and adds no migration. The approved Phase 3.2 architecture stays exactly
as it is: persistent NestJS API (with its WebSocket gateway), persistent worker, Redis/BullMQ, Supabase
Postgres/Storage, the one Netlify site, and the Cloudflare routing Worker. Phase 3.3 (D-36) was rejected and is
not part of this code base.

What changed is how it is deployed: the production setup is written into the repository, so the owner deploys from
the Render, Supabase and Cloudflare dashboards with no terminal, Docker, pnpm or Wrangler.

## Tests

All run on this machine; nothing was deployed and no live service was contacted.

- **Repository checks.** Lint, typecheck, build, route and client-bundle guards: pass.
  - Unit tests: 92, across seven packages.
  - Script tests: 42, including the 10 new deployment-file tests.
  - Integration tests: 210 (database 36, worker 13, API 161), against local Postgres 16 and Redis.
- **Builds from the Dockerfiles as written.** Their build-stage steps run on Node 24.
  - Both builds succeed and carry the certificate at `/app/certs/supabase-ca.crt`.
  - Without the certificate, the build stops.
  - Docker Hub is not reachable from this machine, so the image itself is built by Render.
- **End to end: 35 of 35 checks pass.** This ran in an isolated network that cannot reach the internet. The API
  and worker were the build output, with the exact settings `render.yaml` gives Render, running as uid 1000 (the
  image's `node` user). Postgres served TLS under the pooler's host name, Redis was under the Key Value host name,
  and the real `deploy/cloudflare/worker.js` ran with its `wrangler.toml` settings.
  - **Database state:** the same as the live one (migrations 1–6, then the `bedo_api` login).
  - **D-35 SQL:** `apply-20261006120000.sql` succeeds as one request and the migrator agrees with all 7. `set-super-admin.sql` creates an active Super Admin.
  - **Health:** `health/ready` reports the database and Redis up, and every `bedo_api` database session uses TLS.
  - **Worker:** starts and consumes its queues, and its heartbeat reaches Redis.
  - **Access control:** a direct request without the Worker is refused, while through the Worker the API answers (`CSRF_REJECTED` for a browser GET), and `/`, `/login` and `/admin/login` go to Netlify.
  - **Admin sign-in:**
    - A wrong password is refused.
    - The right password leads to authenticator setup, and bcrypt is replaced by Argon2id.
    - A wrong code is refused; the right code creates the session cookie (`Path=/api/v1/admin`, HttpOnly, Secure, SameSite=Strict).
    - The session works through the Worker, and an admin read without the CSRF header is refused.
    - The next sign-in asks for the code, and no WhatsApp job is created.
    - The API records the visitor's address.
  - **Database password given separately:**
    - Right `PGPASSWORD`: connects.
    - Wrong or missing `PGPASSWORD`: refused.
    - Wrong CA certificate, or a certificate for another host: refused.
- **Wrangler 4.137.0** (the pinned version) accepts `wrangler.toml` in a dry run and bundles the Worker with the three origins.
- **Mutation check.** 13 deliberate mistakes in `render.yaml` and `wrangler.toml` each make the deployment-file test fail. Examples: another region, another eviction policy, a missing or misspelled variable, an extra prompt, port 6543, `sslmode=require`, a password in the URL, auto-deploy on, an invalid plan, the worker without the shared key, a wrong API origin, another Worker name.

**Not tested here:** real Render, real Supabase, real Cloudflare and real Waabek. These are checked after the
deployment, in DEPLOYMENT.md section 0, step 5.
